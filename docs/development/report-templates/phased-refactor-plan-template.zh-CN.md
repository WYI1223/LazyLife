# 分阶段重构计划撰写要求

（3）分阶段重构计划撰写要求

**交付物名称：** 分阶段重构计划（2–4 周，含回归验证与 PR 门禁）
**目标：** 在不显著破坏当前交付节奏的前提下，将模块拆分方案拆解为可执行的阶段任务，明确回归验证、PR 门禁、风险止损与推进机制。
**注意：** 这份文档不是“理想路线图”，而是要让 **TL / TPM / PM / QA / 开发** 都能按它执行与跟踪。

---

## 一、这份计划必须回答的核心问题（必须回答）

前端 TL / Owner 必须在这份计划里明确回答下面 10 个问题：

1. **未来 2–4 周具体分几阶段？每阶段目标是什么？**
2. **每阶段做哪些模块/任务？哪些不做？**
3. **每阶段的完成定义（DoD）是什么？**
4. **哪些任务是关键路径？不完成会卡住后续什么？**
5. **每项任务由谁负责，谁审核，谁协作？**
6. **并行功能开发如何与重构共存？**（冻结策略/接口稳定策略）
7. **每阶段如何回归验证？**（手工/自动化/范围）
8. **什么样的 PR 才能合并？**（PR 模板、review、CI、回滚）
9. **什么时候暂停/止损/缩范围？**（风险阈值）
10. **每周如何汇报与更新计划？**（TPM 跟踪输入）

---

## 二、适用对象（写作视角）

这份计划必须同时服务技术执行和项目推进：

- **TL / 架构负责人**：看技术顺序、关键路径、风险控制是否合理
- **TPM**：看排期、依赖、资源、里程碑、风险状态
- **PM**：看功能冻结/范围调整是否可接受
- **QA**：看回归范围、验证节奏、放行条件
- **开发团队**：看自己该做什么、按什么规则提交 PR

---

## 三、交付标准（必须包含的章节）

建议主文 **5–12 页**（表格为主，少讲故事），附录放模板和清单。
必须包含以下章节：

---

### 0. 文档信息与输入依据（必填）

用于说明计划来源、适用版本、边界一致性。

**必须包含：**

- 项目名称
- 计划负责人（前端 Owner）
- 审核人（TL）
- 协同人（TPM / PM / QA）
- 日期
- 代码基线（branch / commit / tag）
- 关联文档版本：
    - 代码体检报告 vX
    - 模块拆分方案 vX
- 计划窗口（例如：2026-03-01 ~ 2026-03-21）
- 当前约束（发布节点、测试窗口、功能并行开发情况）

---

### 1. 计划摘要（必填，1页内）

给 TPM / TL 快速看懂“怎么执行、风险在哪里”。

**必须包含：**

- 总体执行策略（一句话）
    - 例如：**“先止血+建门禁，再拆核心 P0 模块；高风险阶段由 Owner 主导样板 PR，后续扩展并行执行。”**
- 阶段数（如 3 阶段 / 4 阶段）
- Top 关键路径任务（3–5 项）
- 主要风险（2–4 项）
- 是否需要功能冻结窗口（是/否；冻结哪些模块）
- 对 PM/TPM 的即时请求（如：冻结需求、安排 QA 回归、调整里程碑）

---

### 2. 执行边界与前置条件（必填）

防止“计划一开始就跑偏”。

## 2.1 本次执行范围（Must）

明确本轮纳入的模块（来自拆分方案 Top 优先级）

- 模块 A（原因）
- 模块 B（原因）
- 模块 C（原因）

## 2.2 本次不纳入范围（Won’t）

明确后置模块与原因（发布临近、依赖未稳定、收益不高等）

## 2.3 前置条件（必须写）

重构计划开始前必须满足哪些条件（至少列 3–6 条），例如：

- [ ]  关键模块 Owner 确认
- [ ]  回归清单 v1 已确认（QA/TL）
- [ ]  PR 模板已启用
- [ ]  CI 最低门禁（lint/build）可用
- [ ]  关键接口冻结（如保存接口 / DTO）
- [ ]  本地运行文档可用（至少 Owner + 1人验证）

> 没有前置条件，计划会从第一天开始反复返工。
> 

---

### 3. 分阶段计划（核心必填）

这是整份文档的主干。建议按 **阶段目标 → 任务清单 → 验收标准 → 风险 → 依赖** 的固定格式写。

---

## 3.1 阶段划分建议（2–4 周常用模板）

你可以要求前端 Owner 使用类似下面结构（按实际改）：

### 阶段 0：止血与执行基线（1–3 天）

**目标：** 让重构能被安全执行（不是开始大拆）
**典型任务：**

- 启用重构 PR 模板
- 建立回归清单 v1（至少手工）
- 跑通最低 CI 门禁（lint/build）
- 冻结关键接口（文档化）
- 选 1 个样板模块/样板 PR（Owner 主导）

**阶段 DoD（必须满足）：**

- [ ]  PR 模板启用并在仓库可见
- [ ]  回归清单已确认（QA/TL）
- [ ]  最低 CI 可跑通
- [ ]  样板 PR 合并（可作为后续参考）

---

### 阶段 1：低风险结构拆分（3–7 天）

**目标：** 在尽量不改行为前提下完成“结构止血”
**典型任务：**

- 拆出常量/types/utils（非业务逻辑）
- 提取纯展示组件
- 抽离 service/repository 调用入口
- 清理重复代码（限定范围）
- 为核心路径补最小验证脚本（如未完成）

**阶段 DoD：**

- [ ]  行为无明显变化（按回归清单验证）
- [ ]  所有重构 PR 通过门禁与 review
- [ ]  核心模块外部接口稳定（如页面路由/核心 state 入口不变）
- [ ]  结构文档/边界图更新（如有变化）

---

### 阶段 2：核心 P0 模块拆分（高风险阶段，4–10 天）

**目标：** 处理体检中的核心高风险模块（如日程编辑、笔记详情）
**典型任务：**

- 页面层与状态/控制层拆分
- 校验逻辑/业务流程逻辑抽离
- FFI / 平台调用收口到 service/adapter
- 增补关键路径回归（自动化优先，至少手工可复现）
- 解决拆分中暴露的接口边界问题（受控）

**阶段 DoD：**

- [ ]  核心 P0 模块完成第一轮边界拆分
- [ ]  主流程回归全通过（列明范围）
- [ ]  无新增 P0 blocker
- [ ]  性能/体验无明显退化（至少人工验证）
- [ ]  风险台账更新（已缓解/新发现）

---

### 阶段 3：收口与门禁固化（2–4 天）

**目标：** 防止“拆完又回去”，把规范和门禁落地
**典型任务：**

- 固化 code review checklist
- 增补/调整 lint/import 规则（按需）
- 清理临时兼容代码（能清则清）
- 输出重构结果复盘与后续建议
- 更新模块 Owner 与边界文档

**阶段 DoD：**

- [ ]  新 PR 按模板与门禁执行
- [ ]  关键目录/边界规则文档化
- [ ]  复盘文档完成
- [ ]  剩余债务进入 Debt Log（不留口头债）

---

## 3.2 每阶段必须写的内容（统一格式）

每个阶段都必须包含以下字段（建议表格化）：

- 阶段名称
- 时间窗口（起止日期）
- 阶段目标（1–2句）
- 范围（模块/任务）
- 不包含内容（明确边界）
- 前置依赖
- 负责人（Owner）
- 协作角色（TL/QA/TPM/PM）
- 阶段风险（2–5条）
- 阶段 DoD（完成定义）
- 验证方式（回归/CI/人工检查）

---

### 4. 任务拆解与关键路径（核心必填）

这部分让 TPM 能真正跟踪，不然“阶段”太粗。

## 4.1 任务拆解粒度要求（必须说明）

要求每个任务满足：

- **可在 0.5–2 天内完成并提交 PR**（尽量）
- 有清晰输入输出
- 有明确责任人
- 能验证是否完成

> 不要出现“重构日程模块（5天）”这种不可管理任务。
> 

## 4.2 任务清单（建议表格）

建议字段：

- 任务 ID
- 所属阶段
- 任务名称
- 模块
- 类型（结构拆分/测试/门禁/文档/回归）
- 前置依赖（任务ID）
- 负责人
- 预计工作量（人日）
- 输出物（PR/文档/脚本）
- 验收标准
- 状态（未开始/进行中/阻塞/完成）

## 4.3 关键路径（必须明确）

至少给出一条关键路径链（文字或图）：

- 例如：
`冻结保存接口 -> 建立回归清单 -> 样板PR -> 日程编辑页拆状态层 -> 日程编辑页拆服务层 -> 核心回归 -> 扩展到笔记模块`

并说明：

- 哪些任务延误会影响整体计划
- 哪些任务可以并行
- 哪些任务必须由 Owner/TL 处理（不可替代）

> 关键路径不写清，TPM很难判断“今天卡住是否影响总工期”。
> 

---

### 5. 回归验证计划（核心必填）

这是中期重构能不能稳住的关键。必须明确 **“验证什么、谁验证、何时验证、通过标准”**。

## 5.1 回归策略（必须写）

建议采用“分层验证”：

1. **PR级验证**（作者自测 + Reviewer spot check）
2. **阶段级验证**（阶段结束时核心流程回归）
3. **里程碑级验证**（本轮结束时集中回归）

## 5.2 回归范围定义（至少包含）

### A. 核心主流程（必须）

结合你的产品（日程 + 笔记）至少覆盖：

- 新建/编辑/删除日程
- 新建/编辑/搜索笔记
- 页面跳转与状态保持
- 异常输入/空状态/失败提示

### B. 高风险模块特有场景（必须）

针对本轮拆分模块写专项验证项，例如：

- 日程重复规则校验
- 笔记编辑器切换/保存状态
- 搜索结果与详情联动

### C. 非功能验证（建议）

- 启动/切页是否明显变慢
- UI 卡顿/闪烁
- 崩溃/异常日志是否可定位

## 5.3 回归执行方式（必须明确）

- 手工回归（步骤清单 + 执行人 + 记录方式）
- 自动化回归（如已有：组件测试/E2E smoke）
- 何时执行：
    - 每个高风险 PR 合并前（最小自测）
    - 每阶段结束
    - 本轮收口前

## 5.4 回归通过标准（必须写）

示例（可直接用）：

- 核心主流程用例通过率 100%
- 高风险模块专项验证无 blocker
- 无新增 P0/P1 缺陷（或已记录并有明确处置）
- 与上阶段相比无明显性能退化（人工体验 + 简单指标）

---

### 6. PR 门禁与合并规则（核心必填）

这部分要把你前面提出的“PR完整无误由谁保证”落成流程。

## 6.1 PR 分类与规则（建议）

明确重构期间的 PR 类型（避免混乱）：

- **Type A：纯重构 PR**（不改行为）
- **Type B：重构 + 小范围行为修正**（需显式说明）
- **Type C：功能 PR（非重构）**（受冻结策略约束）

> 重构窗口期建议限制 Type C 在高风险模块内的改动。
> 

## 6.2 重构 PR 必填内容（作者责任）

要求引用你前面模板（建议在计划里再次摘要）：

- 背景/目的（关联体检项或拆分方案条目）
- 改动范围
- 是否影响接口
- 验证方式（手工/自动）
- 风险与回滚
- 关联 Issue / 任务 ID

## 6.3 审核与合并门禁（必须写清责任）

至少明确：

- **作者**：提交完整 PR 描述 + 自测
- **前端 Owner / TL**：技术 review（边界与结构）
- **QA（按风险参与）**：高风险 PR 或阶段末验证
- **CI**：lint/build/test（最低门禁）
- **Code Owner（如配置）**：关键目录必须批准

### 推荐合并门槛（可直接用）

- [ ]  PR 描述完整（模板必填项齐全）
- [ ]  至少 1 名 Reviewer 通过（高风险模块建议 Owner 必过）
- [ ]  CI 全绿（最低 lint/build）
- [ ]  自测记录可复现
- [ ]  涉及核心流程时，回归步骤已执行
- [ ]  可回滚方案明确（至少可回退PR）

## 6.4 禁止事项（建议写入计划）

- 禁止在重构 PR 中混入无关功能
- 禁止在高风险模块绕过 Owner review 直接合并
- 禁止在未更新回归步骤时大改核心交互逻辑
- 禁止“先合并后补文档/补验证”（除紧急修复）

---

### 7. 冻结策略与并行开发协同（必填）

中期重构最容易失败在这里：重构与功能开发互相踩踏。

## 7.1 冻结策略（必须明确）

建议至少写清这 3 类冻结：

1. **模块冻结**（某高风险模块仅允许 bugfix / 重构）
2. **接口冻结**（如保存接口、状态入口、DTO）
3. **窗口冻结**（阶段 2 核心拆分期间，限制并行需求进入）

## 7.2 并行开发协作规则（必须写）

- 新功能尽量落在未冻结模块
- 如必须改冻结模块，需 Owner/TL 审批并同步 TPM
- 优先通过“适配层/接口扩展”降低对重构主线冲击
- 每日同步冲突风险（尤其多人改同目录）

> 这部分写得清楚，TPM推进会轻松很多。
> 

---

### 8. 风险管理与止损机制（核心必填）

不是所有重构都会按计划走，必须预设“何时停、怎么缩”。

## 8.1 风险台账（计划期内）

至少列出本轮执行风险（不是体检风险），字段建议：

- 风险描述
- 触发信号
- 影响
- 缓解措施
- Owner
- 状态
- 升级条件（何时拉 TL/TPM/PM 决策）

## 8.2 止损/降级策略（必须写）

出现以下情况时，触发复盘并可能缩范围：

- 连续 2 个高风险 PR 引入回归
- 核心阶段任务偏差超过预计 30%
- 回归缺陷堆积，QA无法消化
- 并行需求频繁冲入冻结模块
- Owner/TL 带宽不足导致 review 堵塞

可选处置策略（写在计划里）：

- 缩小本轮范围（只保留 Top 1–2 模块）
- 将阶段 2 拆成 2A / 2B
- 暂停结构优化，先补回归与门禁
- 推迟低收益重构项到下轮

---

### 9. 资源、角色与会议节奏（必填）

这部分帮助 TPM 做组织安排。

## 9.1 角色职责（执行期）

明确每个角色在计划执行期间的职责，不要只写头衔：

- 前端 Owner：拆分主导、样板 PR、关键 review、风险上报
- TL：争议拍板、关键架构决策、阶段验收
- TPM：计划跟踪、依赖协调、会议组织、风险升级
- PM：范围取舍、功能冻结确认
- QA：回归清单维护、阶段回归执行/协调
- 开发同学：按任务拆解提交 PR、执行自测

## 9.2 会议与同步机制（建议）

建议最小化但固定节奏：

- **每日 10–15 分钟同步**（执行状态/阻塞/冲突）
- **每周阶段检查**（TL + TPM + Owner + QA）
- **阶段结束验收会**（确认 DoD、更新风险、决定下一阶段）

> 不需要很重，但一定要固定，不然很容易默默偏航。
> 

---

### 10. 度量指标与汇报格式（必填）

TPM 需要可追踪数据，TL 也需要判断治理是否有效。

## 10.1 执行期指标（建议）

至少选择 5–8 个：

- 阶段任务完成率
- 重构 PR 合并数
- 重构 PR 平均 review 时长
- CI 通过率
- 回归通过率（阶段级）
- 新增回归缺陷数（重构相关）
- 高风险模块剩余数量（P0/P1）
- 冻结模块违规改动次数（如能统计）

## 10.2 周报/阶段报告模板（建议）

每周至少输出：

- 本周完成（任务/PR/模块）
- 本周风险变化（新增/缓解）
- 下周计划
- 需要拍板事项（范围/时间/资源）
- 计划偏差（如有）与调整建议

> 这会直接成为 TL → TPM 的高质量输入。
> 

---

### 11. 阶段验收与计划收口（必填）

重构计划不是“做完就算”，必须有收口动作。

## 11.1 每阶段验收（必须）

阶段完成时必须完成：

- 对照阶段 DoD 勾选
- 回归结果记录
- 风险台账更新
- 未完成项处理（转下阶段 / 取消 / 升级决策）

## 11.2 本轮结束收口（必须）

本轮 2–4 周结束后必须输出：

- 已完成拆分项清单
- 未完成项与原因
- 剩余技术债（进入 Debt Log）
- 收益评估（是否达到预期）
- 下一轮建议（继续拆哪些模块 / 暂停治理）

---

## 四、推荐表格模板（可直接要求前端 Owner 使用）

## 五、Flutter + Rust（Windows优先）场景专项要求（建议写进计划）

为了贴合你的项目形态，计划里建议加上这些专项条款：

### 1) FFI / Rust 接口变更控制

- 本轮重构优先 **不改 Rust 接口签名**（如必须改，列为单独任务并提前拍板）
- Flutter 侧先做调用收口与 DTO 映射集中化
- 接口变化要有影响面清单（哪些页面/状态层会受影响）

### 2) Windows 桌面端回归专项

至少把这些纳入阶段回归观察：

- 启动与页面切换是否明显变慢
- 窗口焦点/快捷键/输入行为是否异常（如涉及）
- 崩溃或异常日志是否保留（桌面定位问题靠它）

### 3) 状态管理过渡策略执行

如果当前状态管理混用：

- 本轮只在新拆分模块内执行统一策略
- 老模块不强制一次性迁移
- 在计划中标注“过渡区”，避免团队误解为“全量统一改造”

## 六、这份计划“不合格”的常见表现（TL/TPM 审核标准）

TL 或 TPM 审核时，可以按下面标准快速判断是否打回。

### ❌ 不合格表现

- 只有“阶段名称”，没有任务清单和验收标准
- 没有回归计划，默认“改完看看能不能跑”
- 没有 PR 门禁，靠口头要求
- 没有关键路径，任务都像并行可做
- 没写冻结策略，重构和功能开发会互相踩
- 没有止损机制，一旦延期只能硬扛
- 工时估算全是大块（例如“模块重构 1周”），不可跟踪

### ✅ 合格标准（最低）

- 有阶段划分 + 每阶段 DoD
- 有任务拆解 + 负责人 + 验收标准
- 有回归验证计划（至少手工）
- 有 PR 门禁与合并规则
- 有关键路径与止损机制
- 有周度跟踪与汇报方式

## 九、三份文档之间的关系（验收）

你现在已经有了一套完整链条，验收时可以按这个关系检查是否闭环：

- **（1）代码体检报告**：回答“哪里有风险、为什么”
- **（2）模块拆分方案**：回答“怎么拆、先拆哪里”
- **（3）分阶段重构计划**：回答“谁在什么时候做、怎么验证、什么条件能合并和收口”

如果三份文档之间出现下面问题，就说明还不合格：

- 计划里的任务找不到体检依据（凭空加项）
- 拆分方案的优先级没有进入计划阶段（方案落不了地）
- 回归/门禁没有覆盖体检中的高风险模块（风险没被真正管理）
