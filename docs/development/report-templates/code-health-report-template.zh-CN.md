# 代码体检报告

代码体检报告（高风险模块清单 + 风险等级）

---

**交付物名称：**代码体检报告（高风险模块清单 + 风险等级）

**目标：**在中期换人情况下，用可验证事实识别前端高风险模块，给后续拆分方案和重构排期提供依据。

**注意：**这份报告的任务是“识别问题与风险”，**不是**直接写重构方案（方案放到第 2 份）。

## 一、这份报告必须回答的核心问题（必须回答）

前端 TL / Owner 的报告必须明确回答下面 6 个问题：

1. **当前前端哪些模块最危险？**（高风险模块清单）
2. **为什么危险？**（事实证据，不是主观评价）
3. **风险是什么类型？**（回归/耦合/性能/测试缺失/交付阻塞等）
4. **风险等级是多少？**（统一标准，能比较）
5. **哪些问题需要立即处理，哪些可以后置？**（优先级初判）
6. **本次体检基于哪一版代码、哪一套环境？**（可复现基线）

## 二、报告适用对象（写作视角）

这份报告不是只给前端自己看，要兼顾多角色阅读：

- **TL / 架构负责人**：看技术风险判断是否成立
- **TPM**：看是否需要调整排期、插入治理任务
- **PM**：看哪些需求可能要让路
- **QA**：看后续回归重点在哪些模块
- **接手开发同学**：快速知道“哪里不能乱改”

所以报告要做到：**结论清楚、证据可查、术语统一、可行动**。

## 三、交付标准（必须包含的章节）

这份体检报告建议控制在 **3–8 页主文 + 附录（表格/截图/命令输出）**。

必须包含以下章节（顺序建议如下）：

### 0. 文档信息（必填）

用于锁定基线，避免后续争论“你看的不是这版代码”。

**必须包含：**

- 项目名称
- 体检负责人（前端 Owner）
- 审核人（TL）
- 体检日期
- 体检范围（哪些模块/页面纳入；哪些不纳入）
- **代码基线**（branch / commit hash / tag）
- 运行环境基线（Flutter 版本、Dart 版本、关键依赖版本、Windows 环境）
- 是否可本地运行（是/否；若否写阻塞点）

### 1. 执行摘要（必填，1页内）

给 TPM / TL 快速看懂结论。

**必须包含：**

- 本次体检结论：前端健康状态（绿/黄/红）
- Top 3–5 风险结论（例：核心页面状态与 UI 强耦合、无回归验证、文件过大导致多人冲突等）
- 高风险模块数量（如：P0 x2，P1 x5，P2 x9）
- 是否建议立即插入重构治理窗口（是/否 + 理由）
- 本次体检的边界说明（只覆盖 Windows 主流程前端，不含 Rust Core 等）

> 要求：结论先行，不要一上来讲细节。
> 

### 2. 体检范围与方法（必填）

说明“你是怎么检查的”，让报告可复核。

**必须写清楚：**

### 2.1 体检范围

- 覆盖的模块/目录（例如 `lib/features/schedule/`, `lib/features/notes/`）
- 不覆盖项（例如实验性页面、已冻结模块、待删除代码）

### 2.2 检查方法（至少包含 3 类）

- **静态检查**：代码阅读、目录结构分析、依赖关系、文件大小/复杂度
- **动态验证**：本地运行主流程、观察异常、手工回归关键路径
- **工程检查**：构建、lint、分析器、测试、CI 状态（如有）

### 2.3 使用的工具（如有）

- `flutter analyze`
- `flutter test`
- 代码复杂度/重复代码工具（如 `dart_code_metrics`）
- grep/脚本统计（LoC、TODO/FIXME 数量、文件依赖）
- CI 构建日志（如果已有）

> 要求：不能只写“看了一下代码”，必须说明方法。
> 

### 3. 体检指标与评分规则（必填）

核心是让“风险等级”有统一标准，不靠感觉。

## 3.1 必须包含的评估维度（建议至少 5 个）

每个模块/文件至少从以下维度评估（可 1–5 分）：

1. **复杂度（Complexity）**
    - 文件过大、函数过长、嵌套深、职责混杂
2. **耦合度（Coupling）**
    - UI / 状态 / API / 业务规则混在一起，依赖关系复杂
3. **变更风险（Change Risk）**
    - 高频改动、多人冲突、改一处牵多处
4. **可测试性（Testability）**
    - 难以单测/组件测试、边界不清、副作用多
5. **业务影响（Business Impact）**
    - 是否位于核心主流程、出问题影响大不大

> 可选加分维度：性能风险、平台耦合、可读性/接手成本。
> 

## 3.2 风险等级分级标准（必须统一）

建议采用 **P0 / P1 / P2**（或 高/中/低），但必须定义清楚：

### 推荐定义（可直接用）

- **P0（高风险，需优先处理）**
    - 核心流程模块，且存在明显结构/回归/测试风险
    - 修改成本高且容易引发连锁问题
    - 对交付节奏有直接阻塞风险
- **P1（中风险，建议纳入本轮治理）**
    - 非核心但改动频繁，或结构问题较明显
    - 当前可工作，但继续叠加需求风险会快速上升
- **P2（低风险，可后置观察）**
    - 问题存在但影响有限，短期不阻塞交付
    - 可通过规范约束先控制，不急于重构

## 3.3 评分规则（建议）

用一个简单规则即可（避免过度复杂）：

- 每个维度 1–5 分（5分最差/风险最高）
- 总分区间映射风险等级（示例）：
    - **20–25 分 → P0**
    - **13–19 分 → P1**
    - **5–12 分 → P2**

> 允许“人工上调一档”，但必须写明原因（例如核心登录/数据写入链路）。
> 

### 4. 高风险模块清单（核心必交）

这是这份报告最关键的部分。必须有表格，且字段完整。

**至少列出所有 P0/P1 模块；P2 可汇总。**

## 4.1 必填字段（建议直接做表）

每一行一个模块/文件（优先按“模块”而不是纯文件）：

- 模块/页面名称
- 对应目录/文件（路径）
- 主要功能（一句话）
- 当前问题（事实描述）
- 风险类型（可多选）
    - 结构复杂 / 耦合 / 回归 / 性能 / 测试缺失 / 工程门禁缺失 / 平台耦合
- 风险等级（P0/P1/P2）
- 评分（维度分 + 总分）
- 证据（日志/截图/代码位置/命令输出）
- 近期变更情况（高/中/低；如能统计更好）
- 是否建议进入本轮治理（是/否）
- Owner（当前负责人，如空缺要标“空缺”）

## **4.2 表格模板（可直接复制）**

| 模块/页面 | 路径 | 主要功能 | 当前问题（事实） | 风险类型 | 复杂度 | 耦合度 | 变更风险 | 可测试性 | 业务影响 | 总分 | 风险等级 | 证据 | 本轮治理 |
| --- | --- | --- | --- | --- | --- | --- | --- | --- | --- | --- | --- | --- | --- |
| 日程编辑页 | `lib/features/schedule/...` | 创建/编辑日程 | UI、状态、校验、存储调用混在同一页面；多人改动冲突频繁 | 结构复杂/耦合/回归 | 5 | 5 | 4 | 4 | 5 | 23 | P0 | PR冲突记录、代码片段、回归缺陷 | 是 |
| 笔记详情页 | `lib/features/note/...` | 笔记编辑与展示 | 文件过大、搜索高亮逻辑嵌入UI，测试缺失 | 结构复杂/测试缺失 | 4 | 4 | 3 | 5 | 4 | 20 | P0 | flutter analyze、代码阅读记录 | 是 |

> 注意：**“文件超过 2000 行”只能作为证据之一**，不能单独作为风险结论。
> 

### 5. 关键问题归类分析（必填）

在清单之外，再做一层“共性归因”，帮助第 2 份方案设计。

建议按类别归纳（每类 3–8 条以内）：

### 5.1 结构与边界问题

- 页面层承担过多职责（UI + 状态 + 服务调用 + 业务规则）
- 组件边界不清，复用组件里混入业务逻辑
- `utils` 成为“杂物间”，导致隐式依赖

### 5.2 状态管理问题（Flutter项目建议重点看）

- `setState` 范围过大，局部改动触发整页重建
- 状态散落在多个 Widget，无法追踪数据流
- 同一业务域同时使用多种状态方案（如混用 Provider/BLoC/Riverpod 等）

### 5.3 异步与副作用问题

- API 调用直接写在 UI 生命周期中
- 缺少错误处理/重试/取消逻辑
- 文件 IO / 大计算阻塞 UI（Windows 端卡顿风险）

### 5.4 测试与回归问题

- 核心页面无稳定回归脚本
- 无组件/单测边界，重构难验证
- PR 描述不完整，review 成本高

### 5.5 工程能力问题（如存在）

- `flutter analyze` 有大量 warning 未清理
- 本地构建依赖隐式环境，接手困难
- CI 不稳定/缺失（若已有）

> 这一节要写“共性模式”，不是重复表格内容。
> 

### 6. 风险结论与优先级初判（必填）

这部分是给 TPM 看“后续是否要开治理窗口”的直接输入。

**必须包含：**

- P0 / P1 / P2 数量统计
- 核心主流程涉及的 P0/P1 模块名单
- 建议优先治理的 Top N（通常 3–5 个）
- 不建议立即动的模块（原因：风险高但当前窗口不合适 / 非核心 / 等依赖稳定）

> 注意这里是“初判”，不要展开具体拆分方案（那是第 2 份报告）。
> 

### 7. 附录与证据（必填）

为了让报告可审核、可复盘，必须附证据（不用全贴正文）。

**证据形式建议：**

- `flutter analyze` 输出摘要
- `flutter test` 执行结果（如有）
- 文件行数统计（Top10）
- PR 冲突/回归缺陷记录（如可取到）
- 关键代码截图或片段（少量，标路径）
- 目录结构树（当前 as-is）

> 原则：正文写结论，附录放证据。
> 

## 四、前端 TL / Owner 在体检中必须检查的重点（Flutter 场景专项）

你是 Flutter 前端（Windows 优先），下面这些点建议纳入体检重点，否则容易漏掉真正风险。

### 1) 页面职责是否过重（最常见）

检查是否存在：

- 一个页面文件同时负责 UI、状态、表单校验、API 调用、数据转换、导航跳转
- 大量匿名回调/嵌套 Builder 导致可读性差

### 2) 状态管理是否混乱

检查是否存在：

- 同一个业务域多套状态源（本地 state + provider + service cache）
- 状态更新来源不清，难追踪
- 与 Rust 侧数据接口调用耦合在 UI 层

### 3) 与 Rust / 平台能力的边界是否混乱

检查是否存在：

- Flutter 页面直接处理过多 FFI/平台细节
- DTO 转换逻辑散落多个页面
- 平台差异（Windows 专属）代码侵入通用 UI

### 4) 异步与生命周期风险

检查是否存在：

- 异步回调在页面销毁后仍 setState
- 未处理异常导致页面 silent failure
- 重复请求/竞态导致状态错乱

### 5) 可测试性与回归能力

检查是否存在：

- 没有可独立测试的逻辑层
- 页面行为依赖隐式全局状态
- 核心流程没有最小回归脚本

### 6) 桌面端体验/性能风险（Windows）

检查是否存在：

- 启动/切页卡顿明显
- 大量同步计算在主线程
- 列表渲染/富文本编辑性能问题
- 崩溃日志/错误日志缺失（桌面端定位困难）

## 五、这份报告“不合格”的常见表现（作为审核标准）

TL 审核时可直接按下面否决：

### ❌ 不合格表现

- 只说“代码很乱”，没有证据
- 只列文件行数，没有风险类型和业务影响
- 没有统一风险分级标准（全靠感觉）
- 没有代码基线（不知道基于哪版）
- 把“方案设计/重构计划”提前写进体检报告，导致边界混乱
- 结论无法支持 TPM 做取舍（没有 P0/P1/P2 和优先级初判）

### ✅ 合格标准（最低）

- 有基线
- 有方法
- 有高风险清单
- 有风险等级与评分规则
- 有证据
- 有优先级初判
