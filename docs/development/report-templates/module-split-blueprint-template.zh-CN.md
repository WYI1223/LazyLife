# 模块拆分方案撰写要求

（2）模块拆分方案撰写要求

**交付物名称：** 模块拆分方案（边界图 + 优先级）

**目标：** 基于代码体检结果，明确前端模块边界、拆分原则与优先级，为后续 2–4 周重构计划提供结构蓝图。

**注意：** 这份方案要解决“**怎么拆、先拆哪里、为什么这么拆**”，但**不展开到具体排期与任务**（排期在第 3 份）。

## 一、这份方案必须回答的核心问题（必须回答）

前端 TL / Owner 必须在这份方案里回答清楚下面 8 个问题：

1. **要按什么边界拆？**（页面/组件/状态/服务/领域）
2. **为什么这样拆？**（对应体检里识别出的风险）
3. **拆完后模块职责分别是什么？**
4. **模块之间怎么通信/依赖？**（依赖方向、禁止耦合）
5. **哪些接口需要先稳定/冻结？**（避免边拆边炸）
6. **优先拆哪些模块？为什么？**（优先级与收益）
7. **哪些模块这轮不拆？为什么？**（非目标/后置项）
8. **拆分过程中如何控制风险？**（最小化行为变化、可回退）

---

## 二、适用对象（写作视角）

这份方案既是技术设计文档，也是 TPM/PM 的协作输入，所以写作要兼顾：

- **TL / 架构负责人**：看边界是否合理、与整体架构是否一致
- **前端开发团队**：看拆分怎么落地、哪些规则必须遵守
- **TPM**：看优先级是否合理、是否能拆成里程碑
- **PM**：看是否影响当前需求交付、哪些功能需冻结
- **QA**：看哪些模块拆分后需要重点回归

---

## 三、交付标准（必须包含的章节）

建议主文 **4–10 页**（图 + 表为主），附录可补细节。

必须包含以下内容：

---

### 0. 文档信息与输入依据（必填）

用于说明方案不是凭空设计，而是基于体检结果。

**必须包含：**

- 项目名称
- 方案负责人（前端 Owner）
- 审核人（TL）
- 日期
- 代码基线（与体检报告一致；若不一致要说明变化）
- 关联输入：
    - 代码体检报告版本（v1/v2）
    - 风险清单/技术债条目（如有）
    - 当前约束（排期、功能冻结窗口、发布节点）

---

### 1. 方案摘要（必填，1页内）

给 TL / TPM / PM 快速看懂“怎么拆、先拆哪”。

**必须包含：**

- 本次拆分总体策略（一句话）
    - 例如：**“先分层止血，再按业务域拆分；优先处理核心主流程的高耦合页面，不做全量重写。”**
- 拆分范围（本轮覆盖哪些 feature / 页面）
- Top 3–5 优先拆分对象（模块名 + 原因）
- 预计收益（降低回归风险/提高可维护性/减少冲突）
- 本轮不做项（明确非目标）

> 这部分要让 TPM 看完就知道“能不能推进”。
> 

---

### 2. 设计原则与约束（必填）

先写规则，再画图。否则后面边界很容易漂。

## 2.1 拆分设计原则（至少 5 条）

建议至少覆盖以下原则（可直接用）：

1. **职责单一原则**
    - 页面层负责组装与交互，不承载复杂业务规则与数据访问细节
2. **依赖单向原则**
    - UI → 状态/控制层 → 服务层 → 平台/数据访问（避免反向依赖）
3. **先稳定边界，再重构内部**
    - 优先定义模块接口（输入/输出），内部实现可逐步替换
4. **最小行为变化原则**
    - 拆分阶段尽量不改变用户可见行为（除非明确说明）
5. **可测试性优先原则**
    - 拆出的模块要有明确输入输出，便于单测/组件测试
6. **小步可回退原则**
    - 拆分设计必须支持分阶段落地，不依赖一次性大迁移

## 2.2 当前约束（必须写）

- 交付约束：当前还有哪些功能需求在并行开发
- 技术约束：不能换框架/不能升级大版本/兼容旧状态方案等
- 人员约束：前端人力、QA可投入、TL review 带宽
- 发布约束：是否临近测试/内测/公开发布

> 没有约束的“完美拆分方案”，通常不可执行。
> 

---

### 3. 当前结构（As-is）与目标结构（To-be）对照（核心必填）

这一节是这份方案的“骨架”。

## 3.1 当前结构（As-is）简图（必填）

必须提供一张简图，至少包含：

- 关键页面/feature
- 状态管理位置
- API/服务调用位置
- 主要共享组件/工具
- 明显耦合点（可标红）

> 不要求很精美，但要能看出“问题在哪”。
> 

## 3.2 目标结构（To-be）边界图（必填）

必须提供至少一张 **目标模块边界图**，明确：

- **按业务域划分**（推荐，尤其你的日程 + 笔记场景）
    - `features/schedule`
    - `features/note`
    - `features/search`
    - `features/settings`（示例）
- **按职责分层**
    - `pages` / `presentation`（展示）
    - `state/controller`（状态与交互控制）
    - `services/repository`（数据访问/FFI/API）
    - `models/types`（DTO、view model）
    - `shared/components`（真正可复用）
- **共享层与 feature 层边界**
    - 什么能进 shared，什么必须留在 feature 内

## 3.3 依赖方向规则（必须写明）

至少写清这几条（示例）：

- 页面层可以依赖 feature state / components，但不能直接依赖底层平台细节
- feature state 可以依赖 service/repository，但不能直接依赖 UI 组件
- shared UI 组件禁止依赖具体业务 feature
- Rust FFI / 平台调用统一收敛到 `services` 或 adapter 层，不散落页面

> 这是后面 code review 的依据，不写清楚就执行不动。
> 

---

### 4. 模块拆分清单（必填）

这部分要把“图”落到实际模块级动作，为第 3 份计划做输入。

## 4.1 拆分对象清单（建议表格）

每个“计划拆分对象”至少一行，字段建议：

- 模块名称（建议以业务模块为主，不只写文件名）
- 当前位置（路径）
- 当前问题（引用体检报告要点）
- 目标边界（拆成哪些子模块/层）
- 对外接口变化（有/无；若有写影响面）
- 风险级别（拆分实施风险，不是体检风险）
- 依赖项（需先完成什么）
- 预期收益（可维护性/回归风险/性能/冲突减少）
- 是否纳入本轮（是/否）

| 拆分对象 | 当前路径 | 当前问题（引用体检） | 目标边界（拆成什么） | 接口变化 | 实施风险 | 依赖项 | 预期收益 | 本轮纳入 |
| --- | --- | --- | --- | --- | --- | --- | --- | --- |
| 日程编辑页 | `lib/features/schedule/...` | UI/状态/校验/保存混杂，P0 | 拆为 `page` + `form_state` + `validator` + `schedule_service` | 无（页面路由不变） | 中 | 先明确 DTO 与保存接口 | 回归风险下降，便于测试 | 是 |
| 笔记详情页 | `lib/features/note/...` | 文件过大、搜索高亮逻辑耦合，P0 | 拆为 `viewer` / `editor` / `note_state` / `highlight_logic` | 可能（内部组件 props 调整） | 中高 | 需先冻结编辑器接口 | 提高可读性，减少多人冲突 | 是 |

### 5. 边界定义细则（必须写，避免“拆了但边界仍糊”）

这部分是方案质量高低的分水岭。至少覆盖下面 4 类边界：

## 5.1 页面层边界（Page / Screen）

明确页面层负责什么、不负责什么：

**负责：**

- 路由参数接收
- 页面布局与子组件组装
- 用户交互触发（调用 state/controller）
- 展示状态（loading/error/empty）

**不负责：**

- 复杂业务规则计算
- 持久化/FFI 调用细节
- 数据转换逻辑散落在 UI

## 5.2 状态层边界（State / Controller / ViewModel）

明确：

- 状态数据结构归属
- 事件/动作入口（如 `load`, `save`, `delete`, `search`）
- 异步处理与错误处理归属
- 是否允许直接访问 UI context（通常不建议）

## 5.3 服务层边界（Service / Repository / Adapter）

明确：

- 对 Rust/本地存储/平台能力的调用收口位置
- DTO 转换位置（不要散落多个 widget）
- 错误码/异常转换方式（统一）

## 5.4 共享组件边界（Shared Components）

这是最容易失控的部分，建议明确“进入 shared 的门槛”：

- 至少被 **2 个以上 feature** 稳定复用
- 不依赖具体业务模型/状态
- 提供清晰输入输出（props）
- 不携带业务副作用（如直接保存数据）

> 否则 shared 很快变成“新的大泥球”。
> 

---

### 6. 优先级策略与排序结果（核心必填）

这是 TPM 最关注的内容之一：你不是要拆“所有问题”，而是要给出 **先后顺序与理由**。

## 6.1 优先级判定维度（建议固定）

建议至少使用以下维度（可 1–5 分）：

- **业务影响**（影响核心链路程度）
- **体检风险等级**（P0/P1/P2）
- **变更频率**（近期经常改）
- **拆分收益**（拆完能显著改善什么）
- **实施可行性**（是否能小步落地）
- **依赖阻塞程度**（是否卡住后续其他模块）

## 6.2 排序结果（必须给出明确名单）

至少给出：

- **Top 3–5 本轮优先拆分模块**
- **次优先级候选**
- **本轮不拆列表**（并说明原因）

> 要求：不能只写“按风险高低”，必须说明“为什么现在拆它最划算”。
> 

## 6.3 推荐输出形式（表格）

| 优先级 | 模块 | 原因（风险/收益/依赖） | 前置条件 | 建议策略（先止血/先抽层/先补测试） |
| --- | --- | --- | --- | --- |
| 1 | 日程编辑页 | 核心链路 + P0 + 高频改动 + 多人冲突 | 冻结保存接口、补回归步骤 | 先抽状态与校验 |
| 2 | 笔记详情页 | P0 + 文件超大 + UI与逻辑耦合 | 明确编辑器边界 | 先拆 viewer/editor |
| 3 | 搜索结果页 | 影响跨 feature，耦合重 | 稳定搜索接口 | 先抽 service 与展示组件 |

### 7. 本轮不拆项与冻结策略（必填）

成熟的方案一定会写“不做什么”。

**必须写清：**

- 本轮明确不拆的模块/文件
- 原因（例如：临近发布、风险过高、依赖未稳定、收益不明显）
- 冻结规则（例如：仅允许 bugfix，不允许结构性改动）
- 触发条件（什么时候重新评估纳入拆分）

> 这能防止重构范围失控，也能保护当前交付。
> 

---

### 8. 风险与兼容性说明（必填）

拆分方案不是纯技术美学，要明确潜在风险和控制方式。

## 8.1 拆分实施风险（示例）

- 结构拆分引入行为变化（特别是异步流程）
- 多人并行修改同一模块导致冲突
- 拆分后接口不稳定影响并行功能开发
- 共享组件抽象过度，反而增加复杂度

## 8.2 风险控制策略（必须写）

- 先冻结关键接口（路由参数、状态入口、service 方法）
- 每次拆分只改一类职责（UI / 状态 / 服务）
- 重构 PR 不混入新功能
- 核心流程先有回归脚本（即便手工）
- 关键模块先由 Owner 主导提交首个样板 PR

---

### 9. 方案输出物清单（必填）

为了后续排期和执行，方案文档必须附带这些“可执行产物”：

**至少包含：**

- 目标结构边界图（To-be）
- 拆分对象清单（带优先级）
- 依赖方向规则（文字版）
- 本轮不拆项清单
- 风险控制策略清单

> 这些内容会直接喂给第 3 份“分阶段重构计划”。
>

## 四、Flutter 前端场景专项要求（建议写进方案里）

你们是 Flutter + Rust（Windows优先），方案里建议明确这些“边界设计点”，避免以后返工。

### 1) Flutter UI 与业务逻辑分离要求

- 页面 Widget 不直接做复杂业务规则
- 业务规则集中在状态/控制层或 feature 内逻辑层
- Rust 调用（FFI）不直接散落在按钮点击回调里

### 2) DTO / ViewModel 转换位置

- 明确 DTO（Rust返回）转换成 UI 展示模型的位置
- 不允许在多个页面重复做零散字段映射

### 3) 平台能力收口（Windows 现在先跑通）

- Windows 特有逻辑（如文件路径、窗口行为、快捷键等）收口在 adapter/service
- 页面层不直接依赖平台差异实现

### 4) 状态方案统一策略（非常重要）

如果现在已经混用多种状态管理方式，方案里必须给出策略（哪怕是过渡策略）：

- 本轮是否统一状态方案（通常不建议大改）
- 若不统一，至少规定 **新代码使用哪种方案**
- 老模块迁移策略（渐进式）

## 五、这份方案“不合格”的常见表现（TL审核标准）

TL 审核时可以按下面判断是否打回：

### ❌ 不合格表现

- 只有“建议按模块拆分”，没有 To-be 边界图
- 只按文件行数排序，没有结合业务影响与体检风险
- 没写依赖方向规则，导致后续 review 无法判断“拆得对不对”
- 没有“不拆项”，范围无限扩张
- 方案过于理想化，忽略当前发布/人力约束
- 已经开始写详细工期和每日任务（这是第3份内容）

### ✅ 合格标准（最低）

- 有输入依据（体检报告）
- 有 As-is / To-be 对照图
- 有边界定义（页面/状态/服务/共享）
- 有优先级排序与理由
- 有本轮不拆项
- 有风险控制策略

## 六、建议交付格式（实操）

推荐前端 Owner 交付为：

### 主文（给 TL / TPM / PM）

1. 方案摘要（1页）
2. 设计原则与约束（1页）
3. As-is / To-be 边界图（1–2页）
4. 拆分对象清单 + 优先级（1–2页）
5. 不拆项 + 风险控制（1页）

### 附录（给开发与评审）

- 目录结构草案
- 接口/状态入口草案
- 关键示例（一个模块如何拆）
- 命名/分层规范（如已有可引用）
