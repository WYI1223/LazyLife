  四、PR-0416：atom_overlays + viewMode（S1 R14 + S2）

  Q9：Reconciliation 算法宿主——Rust 还是 Dart？ Rust 需要新增 markdown AST 解析能力；Dart    
  可用 Isolate 但跨 FFI 通信复杂。

    Q9A：建议在Rust端进行Reconciliation算法的实现，这样可以更高效地处理数据，并且Rust的性能优势也更适合这种计算密集型的任务。虽然需要新增markdown AST解析能力，但这是值得的投资。

  Q10：ViewMode enum 成员集合？ source / block / preview 三个 v0.4 落地，inline（Typora 风格）是否预留枚举值？

    Q10A：建议预留inline枚举值，虽然v0.4暂不实现，但可以为未来的功能扩展做好准备。这样在设计上也更具前瞻性。

  Q11：content_rev 同步策略？ atom_update_content 返回值扩展含 content_rev？还是 Flutter 不需要感知具体值，stale 判定完全由 FFI 查询处理？

    Q11A：Flutter 不跟踪，需要时查询

  用户切换到 block 模式时：
    Flutter 调 FFI: atom_get_overlay(atom_id)
    → Core 内部比较 content_rev vs content_rev_at_sync
    → 返回 { block_meta, is_stale: true }
    → Flutter 根据 is_stale 决定是否触发 reconciliation
  - atom_update_content 响应不变
  - 新增 FFI：atom_get_overlay(atom_id) → { block_meta, is_stale, overlay_rev }
  - 优点：EditBuffer 完全不变；stale 判定是 Core 的原子操作，多 pane 场景天然正确
  - 缺点：mode switch 时多一次 FFI 调用（但 mode switch 本身不是高频操作）
