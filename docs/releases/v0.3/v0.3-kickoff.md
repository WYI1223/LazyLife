## 1. 基线变迁审计

v0.3 原始规划制定于 v0.1 时期（2026 年 1 月），基于当时的架构理解。v0.2.5（2026-02-27 闭合）产出了大量新基线，导致原计划的多项假设不再成立。

### 1.1 架构假设变迁

| 维度 | v0.3 原计划假设 | v0.2.5 实际基线 | 影响 |
|------|---------------|----------------|------|
| 状态管理 | 单体 NotesController 管理所有状态 | Coordinator + 6 Managers 模式（PR-0252） | PR-0302/0303/0304 的 file targets 和状态交互需更新 |
| WorkspaceProvider 职责 | WP 管理 tab 状态 + pane 布局 + 树状态 | WP 仅管 pane 布局（166 行，PR-0258） | PR-0301/0303/0304 中写 WP 的假设需修正 |
| Tab 状态归属 | 在 WP 或 Notes controller 中 | NoteTabStateManager（coordinator 内部），per-pane Map（PR-0257） | PR-0303/0304 的 buffer/tab 模型需对齐 |
| Draft/Save 归属 | 在 WP 或 Notes controller 中 | NoteDraftManager + NoteSaveTracker（coordinator 内部） | PR-0303 的 save ordering 需对齐 |
| 跨 feature import | 无自动检查 | CI `architecture_check.dart` 自动检测（PR-0259） | 所有新 PR 必须满足 Rule E，文件 >1,500 行触发 warning |
| Extension Kernel | First-party 将迁移到 Extension Kernel | S5 裁决：First-party 不走 Extension Kernel（third-party only） | **PR-0310 前提假设被推翻** |
| 创建路径 | 两条路径独立工作 | S4 裁决：atom_ref 强制伴随，"未分类"=根级别 ref | PR-0301 前需要先统一创建路径 |
| 数据模型 | `kind`/`type` 枚举驱动渲染 | S1 裁决：view_hint 自动推导 + title/content_type 新字段 | PR-0308 投影逻辑需对齐 S1 |
| FFI DTO | NoteItem 和 AtomListItem 并存 | S8 裁决：统一为 AtomListItem，废弃 NoteItem | 越早执行影响面越小 |
| Provider SPI 交互 | 未指定 | S6 裁决：三层分离（Provider/Orchestrator/Mapping） | PR-0309 设计需对齐 S6 |
| Reminders | 在 `features/reminders/` | S7 裁决：迁移至 `core/reminders/`（已执行 PR-0259） | PR-0308 的触发语义需对齐 S7 |

v0.2.5 产出 8 条语义裁决（S1-S8），其中 4 条需要 v0.3 实现：

|------|---------|---------------|------|

| **S8** | NoteItem→AtomListItem FFI 统一 | **否** — 无对应 PR | 需新增 PR（破坏性变更，宜早不宜迟） |

| 判定 | 含义 |
|------|------|
| **VALID** | Spec 假设无误，可直接执行 |
| **UPDATE** | 核心方向正确，需更新 file targets / 架构假设 / 依赖引用 |
| **REWRITE** | 核心假设被推翻，需重写 spec |
| **DROP** | 前提不成立，建议移除或推迟 |

### 2.2 逐项审计详情

#### PR-0301: Recursive Layout Tree — UPDATE

**有效部分**：递归二叉布局树模型、geometry 约束、序列化方案。这些与架构变更无关，方向正确。

**需更新**：
1. File targets `workspace_provider.dart` — 当前 WP 仅 166 行 pane-layout-only。递归布局树应扩展 WP 或创建新的 `LayoutTreeEngine`（spec 已提及后者，但同时写了 edit WP）
2. **S2 Phase 2 整合**：PR-0301 是 S2 Phase 2（EditorShellService 提取）的自然载体。需要在 spec 中显式化：从 coordinator 提取 tab/draft/save 到 workbench 级 EditorShellService
3. **S4 前置**：atom_ref 强制伴随必须在 PR-0301 之前完成，否则递归树中可能存在无 ref 的 Atom
4. Acceptance Criteria 需追加 S2 Phase 2 验收条件

#### PR-0302: Drag to Split — UPDATE

**有效部分**：edge zone 交互、drop-to-split、min-size rejection。纯 UI 交互层，方向正确。

**需更新**：
1. File targets `note_tab_manager.dart` → 现为 coordinator 内部 manager，路径可能不同
2. File targets `notes_page.dart` → 仍存在但交互方式变化（通过 coordinator 而非直接状态操作）
3. NoteExplorer 1,720 行 — drag 逻辑可能推高。需在 spec 中声明文件大小监控约束

#### PR-0303: Cross-Pane Buffer Sync — UPDATE

**有效部分**：shared buffer per note id、multi-editor subscription、save ordering。方向正确。

**需更新**：
1. `BufferStore` 放置位置：spec 写 `workspace_provider.dart` — **错误**。WP 是 pane-layout-only。Buffer 应在 EditorShellService（S2 Phase 2 产物）或独立 service 中
2. Save ordering 需与 `NoteSaveTracker` 对齐 — 当前 save 状态在 coordinator，buffer sync 需要跨 pane 协调
3. S2 Phase 2 关系：如果 PR-0301 完成了 EditorShellService 提取，PR-0303 的 buffer sync 自然在 EditorShellService 内部实现
4. 依赖调整：PR-0303 实质依赖 PR-0301（EditorShellService 必须先存在）

#### PR-0304: Tab Preview/Pinned — REWRITE

**核心问题**：

1. **前置不存在**：引用 `PR-0205B M2` 作为 "v0.2 已 landed 的 baseline tab semantics"。需要验证此 PR 是否在 v0.2 中实际落地。如果不存在，整个 spec 的 "在已有 baseline 上扩展" 假设不成立
2. **状态归属错误**：
   - Spec 写 "top tab model/state machine" 拥有 preview/pinned 语义
   - 实际：NoteTabStateManager 在 coordinator 内部，per-pane `Map<String, List<String>>`（PR-0257）
   - S2 Phase 2 目标：tab 状态应提升到 EditorGroupModel（workbench 级）
   - **重写方向**：preview/pinned 是 EditorGroupModel 的属性，不是 notes feature 内部状态
3. **File targets 全部过时**：
   - `note_tab_manager.dart` → 应为 EditorShellService 内部模型（PR-0301 产物）
   - `workspace_models.dart` → 可能需要扩展，但不是 tab 状态的持有者
   - `workspace_provider.dart` → pane-layout-only，不管 tab
4. **依赖链调整**：PR-0304 必须在 PR-0301（EditorShellService 提取）之后执行

#### PR-0305: Markdown Perf Gate — VALID

架构无关的纯性能优化。segment rendering、viewport chunk、FPS gate 不依赖任何 v0.2.5 变更。`note_editor.dart` 仍然存在。无需修改。

#### PR-0306: Reliability Hardening — VALID

收尾加固 PR，scope 足够通用（"audit async operations"、"integration regression suite"）。不依赖具体架构假设，自然适配 v0.3 最终状态。

#### PR-0306A: Links Index/Open — VALID

Core/FFI 边界清晰，Migration 10 编号正确（当前 9），link extraction + safe-open 逻辑在 Core service 层。无过时假设。

#### PR-0307: Workspace Launcher — UPDATE

**有效部分**：干净地依赖 PR-0306A。launcher UI + Open All flow + command bridge 不依赖 tab/pane 架构细节。方向正确。

**需更新**：
1. **S3 正交性验证**：必须在 AC 中追加 tag 查询与 explorer 结构正交的验证。S3 裁决要求 tag 是语义分类维度，workspace explorer 是结构归档维度，两者完全独立。launcher 的 "Open All" 需要同时正确处理 tag 过滤结果和 explorer 树节点，不能假设两者有交集关系
2. Launcher flow 打开笔记时需遵循 S4（atom_ref 强制伴随）— 如果 launcher 触发创建动作，必须经由统一创建路径

#### PR-0308: Task-Calendar Projection — UPDATE

**有效部分**：Architecture Note 正确识别了 "calendar blocks are atoms with start_at/end_at set"，避免了不必要的 projection table。方向正确。

**需更新**：
1. S1 对齐：view_hint 自动推导影响 calendar 查询的渲染行为。spec 需声明遵循 S1 R3/R4
2. S7 对齐：Reminders 触发语义改为 Atom 生命周期驱动。spec 需声明 calendar 事件创建/更新后的提醒调度由 Atom CRUD 层统一处理，不在 calendar controller 中
3. File targets 中的 `calendar_projection_service.rs` 和 `calendar_projection_repo.rs` 可能不需要 — Architecture Note 已说明无 RRULE 则无需 projection table。需澄清

#### PR-0309: Google Calendar Provider — UPDATE

**有效部分**：Provider SPI 实现方向正确，与 S6 三层模型基本对齐。

**需更新**：
1. S6 显式对齐：spec 需声明 Provider adapter 不直接接触 external_mappings 表，sync orchestrator 统一管理
2. S1 创建语义：sync pull 创建 Atom 必须遵循 S1（atom_ref 强制伴随 + view_hint 推导 + 指定文件夹路由）
3. 依赖引用过时：`PR-0215` / `PR-0015` 是 v0.1/v0.2 era 编号，应更新为 v0.3 内部依赖
4. 新增依赖：需要 S4（创建路径统一）和 S8（FFI 类型统一）先完成

#### PR-0310: Command Parser Plugins — DROP

**S5 裁决直接推翻此 PR 的前提假设。**

Spec 目标是 "migrate first-party commands/parsers to extension-style plugin form"。但 S5 裁决明确：
- First-party 是产品核心功能，直接 FFI，不经过 Extension Kernel
- Extension Kernel 是 third-party 安全合约
- 强制 first-party 走 Extension Kernel = 为了架构一致性牺牲迭代速度，在当前阶段不合理

**建议**：DROP 此 PR，推迟到 v0.4+（第一个真实 third-party 插件需求出现时）。如果 v0.3 需要对 entry 命令系统做改进（如支持 S4 创建路由），直接在 entry feature 内部重构，不需要 "plugin form" 的间接层。

此外，spec 的 file targets 引用 Core 层的 `command_registry.rs` / `parser_chain.rs` — 这些不存在于 Core 中，命令解析在 Flutter `lib/features/entry/` 中。

#### PR-0311: Global Hotkey — UPDATE

**有效部分**：Windows global hotkey + quick entry toggle 的功能需求仍然有效。

**需更新**：
1. 依赖 PR-0304（需重写）— 重写后的 PR-0304 如果涉及 EditorGroupModel，PR-0311 的 "route to active pane" 需对齐
2. 依赖 PR-0310（建议 DROP）— 如果 PR-0310 被移除，PR-0311 不再需要 "plugin form" 的 entry routing。直接通过现有 CommandRouter 路由即可
3. Pane targeting 需补充：多 pane 模式下 quick entry 结果打开在哪个 pane（active pane / primary pane / create new tab in focused pane）

## 6. 风险台账

### 6.1 已识别风险与 v0.3 解决方案

每个风险必须在 v0.3 内闭环，不推迟到 v0.4。

#### R1: coordinator_impl 文件膨胀 — CI 阻塞风险

- **现状**：`coordinator_impl.dart` 1,514 行（>1,500 warning 阈值）
- **风险**：v0.3 Phase 1 新增方法（EditorShellService 协调、buffer sync 等）可能推至 2,000+ 行触发 CI failure
- **概率**：HIGH
- **归属 PR**：PR-0300D（主缓解）+ PR-0306（兜底）

### 9.3 能力分层

### 9.4 当前结构的四个根本问题

#### 问题 1：PR-0301 承载双重职责

当前 kickoff §2.2 建议将 S2 Phase 2（EditorShellService 提取）整合进 PR-0301。但审视原 spec：

- PR-0301 的 planned files 是 `workspace_models.dart`、`workspace_provider.dart`、新增 `layout_tree_engine.dart` — **纯布局关注点**
- EditorShellService 是状态管理迁移（tab/draft/save 从 coordinator 提走）— **完全不同的关注点**

**能力分层判定**：布局引擎 = L1a，EditorShellService = L1b。它们是 L1 的两个独立子能力，不应捆绑。

**影响**：R5（EditorShellService 复杂度膨胀 PR-0301）的根因就是这个捆绑。

#### 问题 2：PR-0302 drag 逻辑放错位置

当前 spec 的 planned files 包含 `note_tab_manager.dart`、`notes_page.dart` — 假设 drag 逻辑加到 NoteExplorer/NotesPage 中。但：

- Drag-to-split 是布局树层面的交互（"在哪里分"），不是 explorer 的职责（"显示什么"）
- NoteExplorer 已 1,720 行，R2 风险的根因就是关注点放错了位置
- PR-0302 已声明新增 `split_drop_overlay.dart` — overlay 层本身就应该是布局树交互，不是 explorer 内部逻辑

**能力分层判定**：Drag-to-split = L2，依赖 L1a（布局引擎），不依赖 L1b（EditorShellService）。

#### 问题 3：PR-0303 和 PR-0304 被强制串行

当前依赖链：0301→0302→**0303→0304**→0305→0306（6 步串行）。但从能力分层看：

- Buffer 同步 (0303) 依赖 EditorShellService（L1b），不依赖 drag-to-split (L2)
- Tab preview/pinned (0304) 依赖 EditorShellService（L1b），不依赖 buffer 同步 (L2)
- **0303 和 0304 的唯一共同依赖是 EditorShellService，它们之间无依赖关系**

当前串行是因为 v0.1 设计把它们都放在 "Phase 1 串行链" 中。实际上它们可以并行。

#### 问题 4：PR-0306A 被错误归入 Phase 2

链接索引是 L1c 核心基础设施 — 它是 Launcher (L3) 的前置能力。当前方案把 0306A 和 0307 都放在 Phase 2，导致 Phase 2 既有基础设施又有功能。

**能力分层判定**：0306A = L1c，应该在 Phase 1 中与 L1a/L1b 并行执行。
